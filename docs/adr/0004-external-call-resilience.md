# ADR-0004: 외부 호출 장애 대응 전략 (LLM·정보나루·오프라인 폴백)

날짜: 2026-07-06 / 상태: accepted

## Context

골든 패스(이야기 선택→구술→생성→PDF)의 유일한 런타임 실패 지점은 `POST /api/stories/{id}/generate`(LLM 호출)와 `GET /api/sessions/{id}/recommendations`(정보나루+LLM 2차 호출, ADR-0002)다. 규모 추정(동시 사용자 1명, 세션당 외부 호출 ~3회, 하루 피크 ~20세션→~60회/일)상 회로차단기 같은 정교한 장애 대응은 과설계이며, 워크숍 현장에서 아이가 기다리는 실제 인내심 한계가 타임아웃 값의 근거가 되어야 한다.

## Decision

세 계층으로 대응한다.

1. **generate(LLM) 호출**: 타임아웃 15초 + 1회 재시도. 재시도 후에도 실패하면 "다시 말해볼까?" 재입력을 유도(세션 종료 아님).
2. **recommendations(정보나루) 호출**: 타임아웃 8초, 재시도 0회 — 정부기관 API는 지연 시 재시도해도 개선 안 될 가능성이 높아 즉시 `Story.recommend_books`(ADR-0002의 고정 추천)로 폴백.
3. **오프라인 최종 방어선**: 워크숍 현장 인터넷 자체가 끊긴 최악의 경우, `static/fallback_sample.pdf` 1개를 코드에 두고 `GET /api/sessions/{id}/pdf`가 특정 세션 ID(예: `"demo"`)를 받으면 해당 파일을 즉시 서빙. 이 상황의 진행 방식("지금은 인터넷이 불안정해서 예시 작품을 보여줄게요")은 코드가 아니라 운영 매뉴얼로 처리.

## 기각 대안

- **회로차단기·지수 백오프 알고리즘**: 규모(하루 60회 호출)에서 과설계 — 고정 타임아웃값으로 충분.
- **로컬 소형 LLM/규칙 기반 텍스트 생성기로 완전 오프라인 대체**: 4주·1인 백엔드로 감당 안 되는 별도 프로젝트 수준 — 애초에 워크숍 현장은 인터넷이 있다는 전제 위에 있으므로 "최후의 방어선"만 두면 충분.
- **정보나루 재시도 1회 이상**: 정부기관 API 특성상 재시도가 성공률을 크게 개선하지 못할 가능성이 높고, 재시도 대기 시간이 워크숍 흐름을 끊음 — 즉시 폴백이 항상 더 나은 선택.

## Consequences

- 긍정: 실패 지점이 명확히 3계층으로 분리되어 각각 독립적으로 테스트·검증 가능. 워크숍 진행이 끊기지 않음.
- 부정: 타임아웃 15초/8초는 실측 없이 정한 추정값 — 실제 LLM·정보나루 응답 시간 분포를 W2~W3에서 확인 후 조정 필요.
- 리스크: 재도입 조건 — 동시 다수 도서관 운영으로 확장되면(현재 스코프 밖) 회로차단기·캐싱(Redis) 재검토.
